# L2 容器按需增长与容量缩放 —— 设计定稿

> **状态**：已定稿、**尚未改代码**。本文件落档的目的是把讨论收敛成可执行的施工规格。
> **关联**：`TODO.md`「大 L2 缓存初始化不要卡住」、`AGENTS.md` §2.3（L2 不变量）。
> **一句话**：把 L2 容器从"启动时整文件预分配"改成"**按需、按 Slab 整块增长**"，并在此之上把"上次容量 ≠ 本次配置"从**清空重建**改为**缩放保留**（缩放前弹窗确认）。

---

## 1. 背景

### 1.1 用户反馈（现象）

真实反馈：把 L2 开到 **64 GiB 上限**后点「启动加速」——**程序未响应**，任务管理器里 **L2 缓存盘占用率 100% 且持续很久**，等很久之后才恢复。

### 1.2 根因

`SsdCacheService` 构造时调用 `EnsureContainerLength((槽数+1)×4KB)`，对 `cache.dat` 做**整文件预分配**。
文件系统（NTFS / ReFS）在**扩展文件**时，要把新分配区域对上层表现为"全 0"；为此它必须把这批簇**写一遍零**（这正是 `SetFileValidData` 文档里 "without forcing a write of zeros" 所指的默认行为）。64 GiB 全量清零 = **盘 100% + 程序长时间不响应**。

> 说明：本文件把"慢"归因于**零填充**。即使在某些环境里慢的其实是**簇分配本身**，本方案同样成立——因为方案的核心是"**启动时不再需要初始化整文件**"（见 §5.6）。

### 1.3 顺带要解决的旧痛点

上次留下的 L2 容器槽数与本次配置不一致时——改过容量、或缓存盘可用空间变化触发了 `ComputeSlotCount` 的自动夹取——`DetectLedgerMismatch` 会判 `L2Mismatch`，UI 只能问"清空重建？"：**一整层热度经验白扔**。

---

## 2. 目标 / 非目标

**目标**

1. 启动不再因 L2 初始化而卡住（不再有与容量成正比的启动期写盘）。
2. 上次容量与本次配置不一致时**缩放保留**，而不是清空。
3. 不牺牲数据安全判据；不为省掉卡顿而白白增加 SSD 写放大。

**非目标（明确不做）**

1. **运行期热扩容"槽位容量"**（不停服改 `_slotCount`、重建 M 环与元数据数组）。容量只在**启动装载账本**这一刻定，运行期只增长**文件**。
2. **改动容器 / 索引的磁盘格式或版本号**。
3. **把容器改成稀疏文件**（理由见 §3.5）。
4. 本轮不动 `帮助文档.html`。

## 3. 概念对齐

### 3.1 Block / Slot / Slab

| | **Block（块）** | **Slot（槽 / 槽位）** | **Slab** |
| --- | --- | --- | --- |
| 含义 | 缓存的最小数据单元 | 承载一个 Block 的**位置** | 一次获取的**整块**（连续槽区） |
| 大小 | 4 KB（`ServiceConstants.BlockSize`） | 4 KB | 64 MB（`ServiceConstants.SlabSize`）= **16384 槽** |
| 编号 | 全局块号（LBA / SectorsPerBlock） | L1：Slab 内局部索引；L2：**全局槽号** | 按序号分组 |
| 归属 | L1 + L2 | L1 + L2 | **本次起 L1 与 L2 都有** |

一句话：**Slab 是"获取单位"，Slot 是"存放单位"；一个 Slab = 16384 个 Slot。**

### 3.2 为什么 L1 早就有 Slab、L2 没有

- L1 面向**系统内存**：`NativeMemory.Alloc/Free` 的最小单位就是 Slab；且为了能"整块归还系统"，它把空闲栈**按 Slab 分组**（全局单栈没法廉价摘掉某个 Slab 的 16384 个槽位，见 `CacheService` 段注释）。
- L2 面向**一个文件**：槽就是文件里的全局偏移（`(槽号+1)×4KB`），**从不归还空间**，所以只有一张**全局空闲栈**。

### 3.3 本次在 L2 立 Slab

Slab 不特指内存，"一次获取的整块"即可。L2 取同一个量纲（`SlabSize` = 64 MB），作为**容器文件增长 / 收缩的边界**。与 L1 的差别只在职责：

- L1 的 Slab：向系统申请 / 归还内存的单位；
- L2 的 Slab：向文件系统扩展 / 截断的单位。

> 连带：`ServiceConstants.SlabSize` 的注释要从"非托管内存池的 Slab 大小"改成中性表述（L1 内存池与 L2 容器增长共用）。

### 3.4 环 + 空洞（既有事实，非本次改动）

L2 的 M 队列是**环形缓冲**（`_mRing` / `_mHead` / `_mCount`），只支持"入队尾 / 出队头"。写透传的失效可能落在环的**中间**，而环没法 O(1) 从中间删元素，所以只把该槽**标成空洞**（块索引摘掉、`_usedSlots--`、`_holeSlots++`），等 FIFO 顺序推进到它时才 `RecycleHole` 回空闲栈。

- 这是**实现取舍**，不是 S3-FIFO 的要求（S3-FIFO 只有"入队尾 / 出队头"，从不需要中间删除）。
- 连带事实：`FreeSlots` 会比"真正没用过的空量"少，所以准入门槛必须看 `_freeCount` 而不是 `_usedSlots`。

### 3.5 为什么**不**用稀疏文件

稀疏文件把"扩展文件"的开销换成了"填洞"的开销：每往新区域写第一块，文件系统仍要做一次**簇分配记账**，与逐槽增长同构；真正省掉的只有零填充——而零填充可以用 `SetFileValidData` 同样省掉（见 §4 D4），且**不会**让这个会被**随机读**的缓存文件碎片化。故取"整块增长 + `SetFileValidData`"。

### 3.6 VDL（有效数据长度）

`SetFileValidData` 的前提不是"文件系统是 NTFS"，而是"**该卷的文件系统实现并保留 VDL 语义**"：

- **支持**：NTFS、ReFS；
- **不支持**：FAT32、exFAT。

实现上**不预判文件系统**——直接调用一次，失败即门闩（见 D4），自然覆盖"不认识的 FS / 特权被策略禁掉 / 文件被压缩"等全部情形。

## 4. 设计决定（逐条）

### D1 —— L2 引入 Slab，容量规整为整 Slab

- 新增常量 `SLOTS_PER_SLAB = ServiceConstants.SlabSize / BlockSize`（= 16384）。
- `ComputeSlotCount(...)` 的结果**向下取整到 `SLOTS_PER_SLAB` 的整数倍**。
- 容量下限 `MIN_SLOTS`：4096（16 MiB）→ **`SLOTS_PER_SLAB`（64 MiB）**；上限 `MAX_SLOTS` 已是整数倍（64 GiB = 1024 Slab），不变。

**为什么**：增长的批次边界必须干净，否则"整块"名不副实。
**影响**：容量粒度变 64 MB。设置界面本来就按**整 GiB** 配（1–64 GiB，`numSsdCacheGb`），1 GiB = 16 Slab，天然整块，用户无感；只有"按可用空间自动夹取"会向下取整。

### D2 —— 容器按需、按 Slab 整块增长

- 容器初始**只有头部块**（4 KB）。
- 写某槽 `s` 时，若 `(s+2)×4KB > 文件长度`，把文件扩到**该槽所在 Slab 的末尾**：
  `target = BLOCK_SIZE + (s / SLOTS_PER_SLAB + 1) × SLAB_SIZE`。
- 即：**一次扩一个整 Slab**，不是逐槽、也不是一次扩到整容量。

**为什么**：这是修掉"启动卡死"的**主要手段**——启动时最多只建一个头部块，运行期按需扩，且每次最多 64 MB。

### D3 —— 空闲栈填充改"升序"

- `ResetToEmpty` 与 `TryLoadIndex` 两处构建 `_freeStack` 的循环**反向**，使出槽顺序变成 `0,1,2,…`（`PopFree` 是 LIFO，取栈尾）。

**为什么**：若仍按原来的降序出槽，**第一次写入就落到最高槽** → 文件被迫一次撑到顶 → 等于又变回"预分配整容量"。升序才能让文件**从头连续往上铺**。
**影响**：**仅改变"一个块的数据落在哪个容器偏移"**；淘汰顺序由 M 环决定、`_freeCount` 计数不变 ⇒ 准入门槛、命中/淘汰统计、W1、失效行为**全都不变**。空闲栈**不落盘**（装载时由"不在环上的槽"重建），所以**零磁盘/格式影响、零兼容影响**。

### D4 —— 每次扩展"免零填充"，失败即门闩

- 每次 `SetLength(target)` 后**立刻** `SetFileValidData(handle, target)`（把 VDL 推到新长度），使文件系统不必把新区域写零。
- `SE_MANAGE_VOLUME_NAME` 特权**惰性启用一次**（进程 token 改动，用 `static` 锁 + 一次性标志保护，防止构造线程与工作线程并发触发）。
- 任一失败 → 置**实例级**门闩 `_sfvdUnavailable = true`，**本会话**后续所有扩展只做 `SetLength`，并落一条诊断日志。

**为什么**：省掉零填充 = 省掉无谓的 SSD 写放大（约 2×），用户已确认这对硬盘寿命值得。
**安全性**：`SetFileValidData` 之后，未写区域读出来是**磁盘旧内容**。在本程序里这条**不成立风险**：容器槽**必先写、后登记**，而账本只在正常关服时提交（身份戳机制），**未写区域永远不会被当作数据读**（`TryRead` 只读已登记槽；校验器只读账本登记的槽）。

### D5 —— 扩容失败**只停扩容**，不停 L2

- 新增实例门闩 `_growthBlocked`。`GrowToCoverSlot` 失败（多半是卷满）→ 置位 → **该块放弃准入**（走 `AdmitToM` 现有的退回逻辑）。
- **不碰** `_failed`、**不跳过**账本提交。

**为什么**：与 [`DisableAfterIoFailure`](file:///d:/projects/FlyDisk/FlyDisk/Engine/SsdCacheService.cs#L778-L784) 的语义区分开——那条用于**容器读写失败**（写入可能只完成一半 ⇒ 内容不再可信 ⇒ 停用整层 + 跳过账本）。**扩容失败不产生任何不可信内容**：已覆盖范围内的缓存照常命中，账本就是一致的。所以只关掉"扩容"这一项能力。
**细节**：置位后，落在**已覆盖范围内**的空闲槽（主要是回收来的）仍可继续使用；下一次启动重新尝试扩容。

### D6 —— 启动容量不一致 ⇒ **缩放**（不再清空）

- 删除 `DetectLedgerMismatch` 里的"容器槽数 ≠ 当前配置"分支，以及 `DetectIndexParameterMismatch` 的调用。
- `TryReadContainerHeader` **不再校验槽数**（否则永远无法缩放），改为输出容器里记的旧槽数（供日志用）。
- `TryLoadIndex` 支持"**按新槽数装载旧账本**"：
  - 头部校验放宽：只认 `magic / version / blockSize`、`sLimit == 0`、`旧 slotCount > 0`；**不再要求** `mLimit / ghostLimit` 等于当前配置（直接用新配置推导）。
  - M 环条目：`slot >= _slotCount` 的**丢弃并计数**，其余**原槽位不动**。
  - ghost：超出新上限的部分丢弃，**保留较新的那批**（跳过最老的，与 FIFO 语义一致）。
  - 交叉校验改为 **`registered + dropped == usedSlots`**（保住"正文被改过"的检测）。
  - **sanity 上界**：头部计数可能被改坏，必须用**刚读出来的旧头部值**（旧 `slotCount` / 旧 `ghostLimit`）当上界，不能用当前数组长度 —— 否则损坏文件里一个巨大的 `mCount`/`ghostCount` 会变成长时间循环、`_ghostSet` 膨胀。
- 装载成功后，若为**缩容**，把文件截断到"覆盖最大已登记槽并对齐 Slab 边界"（无占用则只留头部块）。

**缩放语义 = 按位置截断**：缩容时保留的是**低槽位**那批块，与热度**无关**（槽号只是容器偏移；热度由 M 环顺序决定）。
**为什么不用"按热度"**：只要要求"真的把文件缩小"，能活下来的必然只有低槽位；按热度保留就得把要留的块**搬到低槽位**（compaction = 按保留容量计的几十 GB 读+写），会在启动时**重新制造卡顿**，与本方案的初衷正面冲突。缩容是"用户改配置"这种低频事件，丢一部分位置偏后的块、让缓存重新学，可接受。

### D7 —— 缩放前弹窗确认（缩 / 扩各一套文案）

- **确认放在 UI 层**（仿既有 `ConfirmL2LedgerUnused` 的"启动前预检"做法），在 `_targetOperationPending = true` **之前**问；用户取消时系统状态一点没动。
- **引擎不再拦**：容量分支删掉后，引擎只按"已确认"执行缩放。→ 必须在相关处留注释说明"**容量缩放的确认由 UI 负责**"，防止将来有人绕过 `Form1` 直接调 `_target.Start` 而静默缩放。
- **触发条件**（全部满足才弹）：① `EnableSsdCache` 为真；② 容器存在且头部合法 → 读到旧槽数；③ 索引也在（`LedgerExists`）；④ **本次实际槽数 ≠ 旧槽数**（容量变了）**或** 发生了**可用空间夹取**（标称 ≠ 实际）。
  - 标称值由 `ConfiguredSlotCountFor`（不夹取）给出，实际值由 `ComputeSlotCountFor`（夹取后）给出，两者不等即"被夹取"。
- **可用空间夹取会单独说明**（2026-10-11 追加）：夹取很可能直接导致缩容（上次没夹取、用户也没改配置，只是缓存盘快满了），
  所以只要发生夹取就弹窗，并在文案里讲清"为缓存盘保留 1 GiB 是必要的——**SSD 快满时读写速度可能明显变慢**"。
- **文案**（中英各一份；参数统一为 `{0}` = 本次**标称**配置、`{1}` = 上次、`{2}` = 本次**实际**、`{3}` = 为缓存盘保留的余量）：

  | 键 | 内容要点 |
  | --- | --- |
  | `dialog.l2Resize` / `dialog.l2Clamp` | 标题：容量变化 / **容量受可用空间限制** |
  | `main.msg.l2ResizeShrink` / `l2ResizeGrow` | 未夹取：上次 {1} → 本次 {2}（较小 / 较大）+ 缩 / 扩后果；是/否 |
  | `main.msg.l2ClampShrink` / `l2ClampGrow` | **被夹取**：配置 {0} 放不下 → 实际 {2}（保留 {3} 的必要性）+ 本次相对上次缩 / 扩；是/否 |
  | `main.msg.l2ClampSame` | **被夹取但容量与上次相同**（罕见）：只说明夹取原因；是/否 |
  | `main.log.cancelledL2Resize` | 已取消启动：用户未确认（未做任何改动） |
  | `main.log.l2ResizeConfirmed` | 已确认缩放：{1} → {2} |

- 按钮 `YesNo`、默认 **No**。
- **已知顺序**：若这份账本同时"需要校验"（盘原本联机 / 上次异常关服），用户会看到**两次弹窗**（先容量 → 后校验）。已知、可接受。
- **夹取预算**（2026-10-11 修正）：`ComputeSlotCount` 的可用空间判据必须把"L2 已占用的空间"加回
  （`budget = free − MIN_KEEP_FREE_BYTES + 容器与索引的文件长度`）。`AvailableFreeSpace` 已扣掉现有 `cache.dat`，
  若不复加，同一份空间会被扣两次、容量被白白夹小（例：现有 4 GiB + 另有 7.1 GiB 空闲，明明够 8 GiB，却被夹到 5.1 GiB）。
  保留量 `MIN_KEEP_FREE_BYTES` 由 2 GiB 调整为 **1 GiB**。

### D8 —— 兼容性：格式与版本号**不变**

- Slab 是**算出来的**（`slabIndex = 槽号 / 16384`），**不落盘**；容器头与索引**不新增字段**。
- `CONTAINER_VERSION`（2）与 `INDEX_VERSION`（3）**不动**；不需要"双格式读取器"或迁移代码。
- 因此"**按最方便的来**"与"**兼容旧版本**"在这里是同一件事：为兼容要额外写的代码 = 0 行。
- 唯一必须改的是 **`L2Verify` 的长度校验**（见 §6 B），但那是**功能本身**要求的，与兼容无关。
- **降级到旧版**不做保证：槽数一变，旧版会判"不匹配"→ 清空重建（安全，丢缓存）。写进文档即可。

## 5. 数据结构与关键流程

### 5.1 常量与新增字段（`SsdCacheService`）

- 常量：`SLOTS_PER_SLAB = ServiceConstants.SlabSize / BLOCK_SIZE`。
- 字段：
  - `long _containerBytes` —— **缓存容器当前长度**。容器读写的比较一律走它，避免每次插块都去碰 `FileStream.Length`（可能是一次系统调用）。
  - `bool _sfvdUnavailable` —— D4 的会话级门闩（实例级）。
  - `bool _growthBlocked` —— D5 的会话级门闩（实例级）。
  - `static readonly object _privilegeLock` + `static bool _privilegeReady` —— 启特权的并发保护。
- **不改**：`_slotCount` 仍是 `readonly`（新值在装载前算好）。

### 5.2 启动装载流程（`SsdCacheService` 构造器）

```
算 _slotCount（配置 → 规整整 Slab）            ← D1
分配元数据数组（按 _slotCount）                 （不变）
DetectLedgerMismatch 判定（仅设备身份/容器可信类） ← D6：去掉容量分支
打开容器（FileShare.None）
containerReady = 长度 ≥ BLOCK_SIZE && 头部可读   ← 头部不再校验槽数
  不 ready → EnsureContainerLength(BLOCK_SIZE)   （重置到只剩头部块）
ledgerTrusted = !source.WasOnline                （不变）
loaded = ledgerTrusted && containerReady && TryLoadIndex(旧容器id)   ← D6：按新槽数装载
  未 loaded → ResetToEmpty（截断到头部块）        ← 并留日志
loaded 且缩容 → 截断文件到覆盖最大已登记槽        ← D6
RotateContainerId()（把新槽数写进容器头）          （不变）
```

### 5.3 写入增长流程

```
WriteSlotFrom(slot):
    GrowToCoverSlot(slot)            ← D2 + D4 + D5
        需要增长时：
            若 _growthBlocked → 返回 false（放弃本块，不停 L2）
            SetLength(target)
            若 !_sfvdUnavailable → SetFileValidData(...)；失败 → _sfvdUnavailable = true + 日志
            更新 _containerBytes
    Position = (slot+1)×4KB ; Write(...)
```

### 5.4 停服（不变）

`Freeze` → 等在途 → `Flush()`（`WriteSnapshot`：容器 `Flush(true)` + 原子替换写入 `index.bin`）。账本里记的 `slotCount / mLimit / ghostLimit` 是**新值**，与容器头一致。

### 5.5 校验器放宽（`L2Verify.cs`）

- 长度校验：从"**必须 == (槽数+1)×4KB**"改为"**至少含头部块 + 覆盖账本里最大占用槽**"（在 `LoadIndex` 之后按 `_slots` 的最大槽校验）。理由：整块增长后长度是"头部 + 整数个 Slab 的已用部分"，且**只长到已用**，不等于整容量。
- `l2v.err.containerLength` 中英文案随口径调整。
- `RotateStamp` 仍要求"≥ 头部块"，保持。

### 5.6 为什么方案不押在 `SetFileValidData` 上

真正的修复是 **D2（按需、按 Slab 增长）本身**：启动时最多建一个头部块。即便 SFVD 完全无效，扩展也只在用到时发生、每次最多 64 MB，**摊到整个会话**，启动期依旧几乎零写盘。SFVD 只承担"省写放大、护 SSD 寿命"这一层，失败回退是纯 `SetLength` + 门闩 ⇒ **计划的正确性不以 SFVD 有效为前提**。

## 7. 兼容性

| 维度 | 影响 | 说明 |
| --- | --- | --- |
| 容器头（`cache.dat` 前 4 KB） | **不变** | 仍 magic / version / containerId / slotCount / blockSize / deviceIdentity / hash；Slab 由槽数推导，不落盘 |
| 索引（`index.bin`） | **不变** | 仍 slotCount / mLimit / ghostLimit + M 环 + ghost；无新字段 |
| 版本号 | **不变** | `CONTAINER_VERSION=2`、`INDEX_VERSION=3` |
| 旧容器文件 | 可读 | 旧文件是"整容量预分配"的；新代码只看头部与索引 |
| 旧账本内容 | 可读 | M 环 / ghost / 空洞语义不变 |
| 旧 `slotCount`（非整 Slab） | 载入不设限 | 只在"新建 / 缩放"时规整；读旧值照旧 |
| 内存占用 | 基本不变 | 只做"整块增长"，仍是单张全局空闲栈 |
| 降级到旧版 | 槽数未变→可用；变了→旧版判不匹配、清空重建 | **安全，丢缓存**（已确认不迁就） |
| `L2Verify` | **需放宽**（§5.5） | 功能本身要求，非兼容需求 |

## 8. 风险与回退

| 风险 | 处置 |
| --- | --- |
| SFVD 不可用（FS 不支持 VDL / 特权被禁 / 文件被压缩） | 门闩 `_sfvdUnavailable`，本会话纯 `SetLength`；功能正确，写放大回 ~2× |
| 启特权失败 | 同上门闩；日志留痕 |
| 扩容时卷满 | 门闩 `_growthBlocked`，**只停扩容**，L2 继续服务已覆盖范围；账本照常提交 |
| 构造期就写不进（`MIN` 64 MiB 都放不下） | 构造失败 → `CacheService` 现有兜底"降级为仅 L1" |
| 损坏的账本计数 | 用旧头部值做 sanity 上界（§5 D6） |
| 缩容后一段时间命中率下降 | 预期：丢的是位置偏后的块；缓存重新学 |

## 9. 验证方式

按项目约定：**代理改完交用户在本地编译 / 验证**，代理不自行编译运行。建议用户验证：

1. 全新开始（无缓存目录）启动 → 观察日志"已新建"，确认启动不卡、日志里 `用时` 很小。
2. 64 GiB 上限配置下启动 → 确认**不再有长时间 100% 磁盘占用**。
3. 改小容量后启动 → 出现**缩容确认弹窗**，选"是"后启动成功、L2 装载并保留部分缓存；选"否"则中止、无任何改动。
4. 改大容量后启动 → 出现**扩容确认弹窗**，确认后旧缓存全部保留。
5. 缓存盘剩余空间不足时触发扩容 → 观察日志"容量不再增长"，且 L2 仍可用。
6. 跑一次「校验/修复 L2」→ 确认放宽后的长度校验不再误判。
7. 正常关服 → 下次启动能载入账本（代次延续）。
